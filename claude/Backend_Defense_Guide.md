## 1. Архитектура в одном экране

SafeRent — это **не монолит на одной машине**, а небольшая распределённая система из
сервисов, общающихся по сети. Это и есть один из главных «взрослых» козырей проекта.

```
                         ┌─────────────────────────┐
        браузер  ──────► │  React SPA (Vite, отд.   │
        (жилец/           │  репозиторий saferent-web)│
        арендодатель/     └───────────┬─────────────┘
        админ)                        │ REST (JSON) + JWT
                                      │ WebSocket (STOMP) для чата/уведомлений
                          ┌───────────▼─────────────┐
                          │   Spring Boot Backend    │  ← ядро, бизнес-логика
                          │   (Java 21, порт 8080)   │
                          └─┬───────┬───────┬──────┬─┘
            JDBC│           │       │       │      │  HTTP
        ┌───────▼──┐  ┌─────▼───┐ ┌─▼─────┐ │  ┌───▼──────────┐
        │PostgreSQL│  │Elastic- │ │MinIO  │ │  │ AI-service   │
        │ (данные) │  │search   │ │(файлы/│ │  │ (Python,     │
        └──────────┘  │(поиск)  │ │фото)  │ │  │ OpenCV+SSIM) │
                      └─────────┘ └───────┘ │  └──────────────┘
                                            │  HTTP
                                   ┌────────▼──────────┐
                                   │ Groq / LLM API    │  ← ИИ-консьерж «Жанибек»
                                   │ (Llama 3.3, облако)│
                                   └───────────────────┘
            ┌──────────┐
            │ MailHog  │  ← перехват писем с OTP-кодом (dev SMTP)
            └──────────┘
```

Всё, кроме React и облачного LLM, поднимается одной командой через
`docker-compose.dev.yml` (PostgreSQL, Elasticsearch, MinIO, MailHog, AI-service, backend).

**Почему такая разбивка (а не «всё в одном Spring»):** каждый компонент решает свою
задачу лучше, чем если бы это делал сам Spring руками: реляционные данные → PostgreSQL,
полнотекстовый поиск → Elasticsearch, бинарные файлы → объектное хранилище MinIO,
компьютерное зрение → отдельный Python-сервис (где живёт экосистема OpenCV/NumPy),
разговорный ИИ → внешний LLM. Это демонстрирует понимание **микросервисной архитектуры**
и принципа «right tool for the job».

## 3. База данных: PostgreSQL + JPA/Hibernate

- **Реляционная БД** PostgreSQL. Все сущности наследуют `AbstractEntity` →
  единый **UUID** первичный ключ (`@GeneratedValue`) и поля `createdAt/updatedAt`
  (проставляются в `@PrePersist`/`@PreUpdate`).
  - *Почему UUID, а не auto-increment Long:* глобально уникален, не раскрывает количество
    записей, удобен в распределённых системах.
- **`ddl-auto: update`** — Hibernate сам создаёт/обновляет таблицы из Java-сущностей.
  - *Плюс:* быстро для разработки и диплома. *Минус (честно сказать):* для продакшена
    так нельзя — там нужны миграции (Flyway/Liquibase), потому что `update` не умеет
    удалять/переименовывать безопасно.
- **Ключевые сущности:** `User`, `Apartment` (+ `apartment_amenities`,
  `apartment_panoramas` как `@ElementCollection`), `District`/`DistrictRating`, `Booking`,
  `Contract`, `Payment`, `Wallet`/`WalletTransaction`, `Chat`/`Message`,
  `InspectionPhoto`, `Report`, `Favorite`, `Notification`.
- **Связи:** `@ManyToOne` (квартира → арендодатель, → район), `@OneToMany`, `@OneToOne`
  (кошелёк → пользователь). Ленивая загрузка (`FetchType.LAZY`) где можно.
- **Soft delete:** у квартир есть `deletedAt` — записи не удаляются физически, а помечаются.
  *Плюс:* история сохраняется, можно восстановить, ссылки не ломаются.
- **Деньги — `BigDecimal`** (а не double): точность до копейки, без ошибок плавающей точки.

**Возможный вопрос:** «Почему реляционная, а не NoSQL?» → У нас сильно связанные данные
(пользователи↔квартиры↔договоры↔платежи) и нужны транзакции (эскроу, кошелёк) — это
классический случай для SQL. NoSQL взяли бы для слабоструктурированных данных или огромного
объёма, чего тут нет.

## 4. Аутентификация и безопасность

- **JWT (JSON Web Token)** на базе `jjwt`. При логине сервер выдаёт подписанный токен
  (секрет + срок 24 ч). Дальше каждый запрос несёт `Authorization: Bearer <token>`.
- **`JwtFilter`** перехватывает запрос, валидирует токен, кладёт `User` в
  `SecurityContext`. Дальше в любом сервисе текущий пользователь берётся через
  `SecurityUtils.getCurrentUser()`.
- **Stateless** (`SessionCreationPolicy.STATELESS`): сервер не хранит сессии — токен
  самодостаточен. *Плюс:* масштабируемость. *Минус:* токен нельзя мгновенно отозвать
  (решается коротким сроком жизни / блек-листом).
- **Пароли — BCrypt** (`PasswordEncoder`): хранится только хеш с солью, не сам пароль.
- **Роли:** `PreferredRole` (TENANT/LANDLORD) + флаг `admin`. Защита эндпоинтов через
  `@PreAuthorize("hasRole('ADMIN')")` и правила в `SecurityConfig`. Часть эндпоинтов
  публичная (лента, поиск, просмотр квартиры), остальное — только авторизованным.
- **CORS** настроен на dev-origin фронта (5173/3000).

## 5. «СМС на почту» — на самом деле OTP по email

Это **подтверждение через одноразовый код (OTP)**, отправляемый **на email** (не SMS).

**Как работает (`OtpServiceImpl`):**
1. Генерируем 6-значный код: `String.format("%06d", random.nextInt(1_000_000))`.
2. Кладём код в память (`ConcurrentHashMap<userId, {code, expiresAt}>`) со сроком **10 минут**.
3. Отправляем письмо через `JavaMailSender` (Spring Mail) на SMTP.
4. В dev SMTP — это **MailHog**: он перехватывает все письма и показывает их в веб-интерфейсе
   на `localhost:8025` (реальные письма никуда не уходят — удобно и безопасно для демо).
5. При вводе кода `verifyOtp` сверяет код и срок, затем удаляет его (одноразовость).

**Плюсы:** просто, бесплатно, наглядно на защите (открыл MailHog — показал письмо).
**Минусы / honest:** код хранится **в памяти процесса** — при рестарте теряется и не
масштабируется на несколько инстансов (в проде → Redis с TTL). И это **email, а не SMS** —
для настоящего SMS нужен платный шлюз (Twilio, Vonage, локальный агрегатор); архитектурно
заменяется одной реализацией `OtpService`.

## 6. Хранилище файлов — MinIO (вместо «папки на диске» или блобов в БД)

- **MinIO** — это **S3-совместимое объектное хранилище** (тот же API, что у Amazon S3,
  но self-hosted и бесплатно). Фото квартир и панорамы 360° грузятся туда через
  `FileStorageService` (`io.minio` SDK), а в БД хранится только **URL**.
- *Почему не хранить картинки в PostgreSQL:* блобы раздувают БД, замедляют бэкапы и
  запросы. Объектное хранилище для этого и создано.
- *Почему не просто папка на сервере:* S3-подход даёт масштабируемость, раздачу по HTTP,
  совместимость с облаком — можно потом переключить на реальный AWS S3 без смены кода.
- **Тонкость с хостами (хороший аргумент про сети Docker):** в БД ссылки содержат
  `localhost:9000` (чтобы их открывал браузер пользователя), но изнутри docker-сети тот же
  MinIO доступен как `minio:9000`. Поэтому AI-сервис при скачивании фото подменяет хост
  (`MINIO_PUBLIC_HOST → MINIO_INTERNAL_HOST`). Это показывает понимание разницы между
  внутренней и внешней адресацией контейнеров.
- Бакет `saferent-photos` создаётся автоматически (`minio-init`) и открыт на чтение
  (`anonymous download`).

## 7. Поиск — Elasticsearch (и почему у тебя сейчас «не находит»)

### Как устроено
- Квартиры **индексируются** в Elasticsearch как `ApartmentDocument` (индекс `apartments`):
  поля `title`, `description`, `address` — тип **Text** с анализатором `standard`;
  `price/area/rooms/districtId` — для фильтров.
- Поиск (`ApartmentSearchService.search`) строит **bool-запрос**:
  - `multiMatch` по `title^3, description, address^2` (цифра — буст важности поля),
  - **`fuzziness("AUTO")`** — вот это и есть устойчивость к опечаткам,
  - фильтры по цене/району/комнатам + всегда `status = ACTIVE`.
- **`fuzziness AUTO`** = расстояние Левенштейна: для слов длиной 6+ символов допускает до
  **2 правок** (вставка/удаление/замена/перестановка букв). Поэтому теоретически
  «Студея квортира» должно находить «Студия квартира» (по 1 замене в каждом слове).

### Почему ES, а не SQL `LIKE '%студия%'`
- `LIKE` **не умеет опечатки** и ранжирование, медленный на больших объёмах, не учитывает
  морфологию. Elasticsearch даёт fuzzy-поиск, релевантность (score), скорость на инвертированном
  индексе. Это «правильный инструмент» для текстового поиска.

### Почему у тебя сейчас ничего не находит — 3 вероятные причины (по убыванию)
1. **Квартира не верифицирована.** В индекс попадают **только `verified == true` И
   `ACTIVE` И не удалённые** (см. `ApartmentSearchService.index()` и `reindexAll()`). Новое
   объявление по умолчанию `verified = false` → его в индексе нет → поиск пустой. **Это самая
   частая причина.** Зайди админом и верифицируй квартиру.
2. **Индекс пустой / устарел.** `reindexAll()` вызывается на старте (`DataLoader`), но если
   Elasticsearch не был поднят в момент старта бэкенда — переиндексация пропускается (в логах
   `Elasticsearch unavailable: skipping reindex`). Подними ES, затем перезапусти бэкенд.
3. **Elasticsearch не запущен.** Тогда `search()` молча возвращает пустой список (сделано
   намеренно, чтобы приложение не падало без ES).

### Как быстро проверить (диагностика)
```bash
curl http://localhost:9200/_cat/indices?v                 # есть ли индекс apartments
curl http://localhost:9200/apartments/_count              # сколько документов в индексе
curl "http://localhost:9200/apartments/_search?q=студия"  # ищет ли вообще
```
Если `_count` = 0 → проблема в индексации (причина 1 или 2), а не в запросе. Если документы
есть, но fuzzy не ловит — можно повысить устойчивость, добавив `minimum_should_match` и явный
`fuzziness` на оба слова, но сперва убедись, что данные в индексе.

**Минусы ES (honest):** eventual consistency (индекс обновляется отдельно от БД — рассинхрон
возможен), требует памяти (у нас 512 МБ heap), ещё один сервис в обслуживании.

## 8. ⭐ ИИ в проекте — ГЛАВНОЕ (две РАЗНЫЕ вещи, не путать!)

Комиссия будет спрашивать про ИИ — здесь нужно говорить **точно и честно**. В проекте
**две независимые «умные» части**, и это разные классы технологий:

### 8.1. Анализ состояния квартиры — это **классическое компьютерное зрение (SSIM), НЕ нейросеть**

**Честный ответ комиссии:** «Это **не** обученная ML-модель и **не** нейросеть. Это
**детерминированный алгоритм компьютерного зрения** — SSIM поверх OpenCV. Мы сознательно
выбрали его, потому что он **объясним** и **не требует датасета для обучения**.»

**Что такое SSIM (Structural Similarity Index):** метрика похожести двух изображений,
которая, в отличие от простого попиксельного вычитания, имитирует человеческое восприятие и
сравнивает картинки по **трём составляющим**: **яркость (luminance)**, **контраст (contrast)**
и **структура (structure)**. Результат — число от −1 до 1 (1 = идентичны).

**Как работает наш `ai_service` (`/compare`, Python + OpenCV + scikit-image), по шагам:**
1. Скачивает два фото (до заселения / после выезда) из MinIO.
2. Приводит к одному размеру (`cv2.resize`) и в оттенки серого (`cvtColor`).
3. Считает `ssim(before, after, full=True)` → **score** + карта различий (diff map).
4. Бинаризует карту различий (`threshold` + Otsu) и ищет **контуры зон изменений**
   (`findContours`), отбрасывая мелкий шум (`contourArea > 50`).
5. Выносит вердикт по порогам: `score ≥ 0.92` → нет повреждений; `0.70–0.92` → незначительные
   изменения; `< 0.70` → существенные повреждения. Возвращает `ssimScore`, число зон,
   текстовое описание.
6. Backend (`AiAnalysisClient`) забирает результат и использует его в логике инспекции/эскроу.

**Плюсы:** не нужен датасет и обучение; быстро и дёшево; **полностью объяснимо** (можно
показать diff-карту); работает офлайн. **Минусы (сказать самой, это показывает зрелость):**
чувствителен к освещению и ракурсу (поэтому фото выравниваем по размеру); не «понимает»
семантику («это царапина на стене») — лишь измеряет, насколько пиксели структурно изменились;
смена мебели засчитается как «изменение». Для семантики нужна была бы обученная CNN/детекция
объектов — это перспектива развития.

### 8.2. ИИ-консьерж «Жанибек» — это **большая языковая модель (LLM) через API**

**Честный ответ:** «Это **предобученная нейросеть** (LLM на архитектуре *трансформер*),
но **мы её не обучали и не дообучали** — мы используем готовую модель как сервис через API
(сейчас **Llama 3.3 70B через Groq**). Наша инженерия — это **prompt engineering** и
**function-calling (агент)**, а не тренировка модели.»

**Ключевые понятия для защиты:**
- **LLM / трансформер** — нейросеть, предсказывающая следующий **токен** (кусочек слова) по
  контексту; обучена на огромных текстовых корпусах. Примеры: GPT, Llama, Gemini.
- **Почему не обучали свою модель:** обучение LLM требует тысяч GPU, терабайтов данных и
  months — для дипломного проекта это нереалистично и не нужно. Индустрия так и делает:
  берут готовую модель и **адаптируют через промпт и инструменты**.
- **Function-calling (это и есть «изюминка»):** мы описываем модели **инструменты**
  (`searchApartments`, `explainEscrow`, `getMyTenancyStatus`). Модель сама решает, какой
  вызвать, возвращает имя функции и аргументы; **наш backend исполняет** функцию (под Spring
  Security, от имени текущего пользователя), отдаёт результат обратно — и модель формулирует
  ответ. То есть ассистент **реально ищет квартиры и читает данные пользователя**, а не
  выдумывает. Это паттерн **AI-агента**.
- **Почему не RAG с векторной БД:** данные у нас **структурированные** (квартиры, договоры в
  PostgreSQL), поэтому прямые вызовы функций точнее и проще, чем векторный поиск по тексту.
  RAG имеет смысл для слабоструктурированных документов.
- **Провайдер за интерфейсом `LlmClient`:** реализации `GroqClient` / `GeminiClient`
  переключаются конфигом `ai.provider`. Это **слабая связанность** — можно заменить ИИ-движок
  (хоть локальный Ollama) без правок бизнес-логики.
- **Трёхъязычность:** ассистент отвечает на RU/EN/KK — язык передаётся из интерфейса в
  system-промпт.

**Плюсы:** мощный современный ИИ почти бесплатно; не нужно обучение; агент совершает реальные
действия. **Минусы (honest):** зависимость от внешнего API (сеть, лимиты); возможны
«галлюцинации» — мы их гасим тем, что факты модель берёт **только из инструментов**, а в
промпте запрещено выдумывать; качество казахского у Llama слабее, чем русского.

### Итоговая формулировка для комиссии (выучить!)
> «В проекте две ИИ-составляющие разного класса. Первая — анализ состояния квартиры — это
> **классический алгоритм компьютерного зрения SSIM** (детерминированный, объяснимый, без
> обучения). Вторая — консьерж «Жанибек» — это **готовая большая языковая модель**,
> используемая через API; **мы её не тренировали**, а построили вокруг неё **ИИ-агента с
> function-calling**. Свою модель не обучали сознательно: это требует ресурсов уровня
> дата-центра и не входит в задачи проекта.»

## 9. Реал-тайм: WebSocket + STOMP

- Чат между арендатором и арендодателем и **push-уведомления** работают по **WebSocket**
  (протокол STOMP поверх него). Клиент подписывается на топик (`/topic/users/{id}`), сервер
  пушит сообщения/уведомления мгновенно.
- *Почему не HTTP-поллинг:* не нужно дёргать сервер каждые N секунд — меньше нагрузки,
  доставка моментальная.
- Фото и эмодзи в чате; уведомления о бронированиях, договорах, платежах.

## 10. Бизнес-контур: бронь → договор → эскроу → кошелёк

- **Бронирование** (`Booking`) → **договор** (`Contract`, двухсторонняя e-подпись) →
  **платежи** (`Payment`: депозит + помесячная аренда, расписание `RentPeriod`).
- **Эскроу:** депозит «замораживается» на нейтральном счёте; админ решает возврат
  арендатору / компенсацию арендодателю по итогам инспекции.
- **Кошелёк** (`Wallet` + `WalletTransaction`) — **леджер**: каждое денежное событие пишет
  транзакцию со знаком и `balanceAfter` (пополнение, оплата аренды, доход, возврат депозита,
  компенсация, бонус). Единый источник правды по деньгам.
- **Платежи — mock** (реальных денег нет; так и говорить — это симуляция платёжного контура,
  что нормально для диплома).

## 12. Как организован код (слоистая архитектура)

```
controller  → принимает HTTP, валидирует, отдаёт DTO        (тонкий слой)
service     → бизнес-логика (interface + impl)              (ядро)
repository  → доступ к БД (Spring Data JPA)                 (данные)
dto         → объекты запроса/ответа (не отдаём сущности наружу)
mapper      → MapStruct: сущность ↔ DTO
entity      → JPA-сущности (таблицы)
```
- **Почему DTO, а не отдавать Entity:** не раскрываем внутреннюю структуру/пароли, не тащим
  ленивые связи в JSON, контролируем контракт API.
- **Интерфейс + реализация** у сервисов — слабая связанность, тестируемость (Mockito).
- **Swagger UI** (`/swagger-ui.html`) — автodocs всех эндпоинтов.
- **Тесты:** юнит-тесты на Mockito (без поднятия внешних сервисов); контекстный
  `ApplicationTests` исключён из обычного прогона (требует живых PostgreSQL/ES).

## 14. ⭐ FAQ комиссии — короткие выученные ответы

**— Это настоящий ИИ или просто API?**
Две части. Анализ фото — классический CV-алгоритм SSIM (без нейросети). Консьерж — настоящая
нейросеть (LLM), но используем готовую через API и строим над ней агента; свою не обучали
осознанно (нужен дата-центр).

**— Вы обучали модель?**
Нет. Обучение LLM требует тысяч GPU и огромных датасетов. Современный подход — брать готовую
модель и адаптировать промптом и инструментами (function-calling). Именно это мы и сделали.

**— Что такое function-calling / почему ассистент не врёт?**
Модель не выдумывает данные, а вызывает наши функции (поиск квартир, статус платежей). Backend
исполняет их под Spring Security и возвращает реальные данные; в промпте запрещено выдумывать.

**— Что такое SSIM и чем он лучше попиксельного сравнения?**
Метрика структурного сходства: сравнивает яркость, контраст и структуру окнами, ближе к
человеческому восприятию; устойчивее к шуму, чем простое вычитание пикселей.

**— Почему Elasticsearch, а не поиск в SQL?**
Нужны опечатки (fuzzy), релевантность и скорость по тексту — SQL `LIKE` этого не умеет.

**— Почему JWT, а не сессии?**
Stateless: сервер не хранит состояние, легко масштабировать. Минус — токен нельзя мгновенно
отозвать (гасим коротким сроком жизни).

**— Где храните фото и почему не в БД?**
В MinIO (S3-совместимое объектное хранилище). Блобы в БД раздувают её и замедляют бэкапы.

**— Почему микросервисы?**
Каждой задаче — свой инструмент: SQL для данных, ES для поиска, MinIO для файлов, Python для
CV, LLM для диалога. Слабая связанность, заменяемость компонентов.

**— `ddl-auto: update` — это нормально для прода?**
Нет, для прода нужны миграции (Flyway/Liquibase). Для разработки/диплома `update` ускоряет работу.

**— Платежи настоящие?**
Нет, это симуляция платёжного контура (mock) с полноценной бизнес-логикой эскроу и кошелька-леджера.

### Перед защитой — чек-лист «чтобы всё работало на демо»
1. Подними инфраструктуру: `docker compose -f docker-compose.dev.yml up -d`.
2. Дождись, пока Elasticsearch станет healthy, **затем** перезапусти backend (чтобы
   `reindexAll()` отработал) — иначе поиск пустой.
3. **Верифицируй** пару квартир под админом — только тогда они появятся в поиске.
4. Проверь, что AI-service (`/health`) и Groq-ключ заданы — иначе инспекция и Жанибек не
   ответят.
5. Прогони сценарий: регистрация+OTP → поиск → бронь → договор → оплата → инспекция → отзыв,
   и спроси что-нибудь у Жанибека на трёх языках.
